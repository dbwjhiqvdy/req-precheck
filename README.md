# 需求预审工具（req-precheck）

> 用 LLM 按 DoR（需求就绪定义）标准，对游戏研发需求做**评审前预审**：逐项判定 8 条标准、指出缺失项、给出理由——并且**能评测它自己准不准**。

## 这个工具解决什么问题

需求评审最常见的失败是"会上大家点头通过，开发到一半发现没定义清楚"。根因不是没人评审，而是**评审标准没有被稳定执行**：同一份需求，不同人、不同时间，判定结果可能不一样。

本工具把《游戏项目研发流程规范》里的 DoR 8 项清单**写成代码里的规则**（`rubric.py`），再让模型照规则逐项判定，最后用人工标注的数据**量化它的准确率、漏判率、误拦率**。

**它的价值不在"能自动评审"，而在"知道自己错在哪、错多少"。**

## 快速开始

```powershell
cd E:\项目\项目管理\req-precheck

# 1) 不用 Key 先跑通流程（结果仅供验证管道，不能当结论）
python precheck.py --prompt v2 --mock

# 2) 配置真实 Key（在项目根目录新建 .env，写入一行）
#    DEEPSEEK_API_KEY=你的key

# 3) 真实调用（20 条需求约消耗几万 token）
python precheck.py --prompt v2

# 4) 评测（需要先完成 data/labels.jsonl 的人工标注）
python evaluate.py --results results/precheck_v1.jsonl results/precheck_v2.jsonl --labels data/labels.jsonl
```

```
├── precheck.py                    预审主程序（v1 / v1b / v2 三个 prompt 版本）

├── .env.example                   配置模板（提交进仓库；.env 不提交）
├── data/
│   ├── requirements.jsonl         30 条模拟游戏需求（质量参差）

```

## 五个设计决策

**1. 零第三方依赖**
只用标准库（`urllib`）调 API。理由：这是要给别人跑的工具，**"clone 下来就能跑"比"功能多"重要**。要换官方 SDK 只需替换 `llm.py` 里的一个函数。

**2. 三个 prompt 版本，用来做**可分离**的消融对比**
同一份数据、同一个模型，**只改 prompt**：
- `v1` 朴素写法（"请判断是否满足需求就绪标准"）——**不给输出格式**
- `v1b` 只给输出 schema ——**不给规则细节与判定纪律**
- `v2` 工程化写法：完整结构化规则 + 明确输出 schema + **规定"不确定时判未通过"** + **要求引用原文片段作为理由**

这样拆的好处：`v1 → v1b` 的差异 = **输出格式的价值（可用性）**；`v1b → v2` 的差异 = **规则与纪律的价值（准确性）**。
只比 `v1` 和 `v2` 会把两个效果混在一起，导致结论说不清是"能用"还是"更准"。

**3. 判定缺项一律视为"未通过"**
模型没返回某一项、或返回了非布尔值，一律按未通过处理（`precheck.py` 的 `normalize_items`）。
理由：DoR 的代价是不对称的——**漏放一条未就绪的需求，代价是开发返工；误拦一条已就绪的，代价只是补一次说明**。

**4. MOCK 模式带"防误用"机制**
`--mock` 不联网、用关键词启发式伪造输出，输出文件名强制带 `_MOCK`，评测报告加 `_MOCK_` 前缀并打印警告。
理由：**假数据最危险的地方不是假，而是被当成真**。

**5. 模块名绝不与标准库同名（踩坑记录）**
结果查看器原本叫 `inspect.py`——它遮蔽了标准库的 `inspect` 模块，导致**同目录下所有脚本**在 `argparse` 初始化时崩溃：

```
AttributeError: module 'inspect' has no attribute 'signature'
  (consider renaming '...\req-precheck\inspect.py' since it has the same name
   as the standard library module named 'inspect' and prevents importing it)
```

原因：Python 会把**脚本所在目录**放在 `sys.path` 最前，于是第三方库内部的 `import inspect` 导到了我的文件。
教训：**项目根目录里放 `inspect.py` / `json.py` / `types.py` 这类文件等于埋雷**——报错出现在完全无关的第三方代码里，定位成本极高。已改名 `show_results.py`。

## 结果（真实调用，30 条数据集，2026-10-05）

**实验设计**：同一份数据（30 条模拟需求，其中人工判「就绪」9 条）、同一个模型（`deepseek-chat`）、同一套规则，**只改 prompt**。

| 版本 | prompt 内容 | 准确率 | 漏判率 | 误拦率 | 解析异常 |
|---|---|---|---|---|---|
| `v1` | 只给任务，不给输出格式 | 70.0% | 0.0% | 100.0% | 30/30 |
| **`v1b`** | 给输出格式，不给规则细节与纪律 | **93.3%** | 4.8% | **11.1%** | 0/30 |
| `v2` | 格式 + 完整规则 + 判定纪律 | 86.7% | 4.8% | 33.3% | 0/30 |
| —— | **懒惰基线：永远判「不就绪」** | 70.0% | 0.0% | 100.0% | —— |
| —— | 懒惰基线：永远判「就绪」 | 30.0% | 100.0% | 0.0% | —— |

完整报告：[`reports/eval_comparison.md`](reports/eval_comparison.md)

### 四条结论

**1. `v1` 的成绩仍然精确等于「什么都不做」**（70% / 0% / 100%）。
原因与本轮设计一致：**没有指定输出格式**——30 条全部无法按规则 id 解析（`SCHEMA_ID_MISMATCH`），被强制记为"全部缺失"，于是等价于"一律打回"。
→ **它产生的是零可用信息，不能用"准确率 70%"来描述它。**

**2. prompt 工程的价值被证实了一半：让输出可用（`v1` → `v1b`，+23.3 个百分点）**
解析异常从 30/30 降到 0/30，误拦率从 100% 降到 11.1%。这部分证据很强。

**3. 「加规则 + 加纪律」仍未证明有效——但这次找到了机制性原因**
`v1b` 与 `v2` 只有 **2 条**判定不同（R04、R26）。其中 R04 是最关键的一条：**`v2` 明确识别出这是工程类需求、明确引用了例外条款，却主动推翻了它。** 它的原话：

> 「本需求为工程/工具类需求（CI 校验脚本），按规则**可**判为不适用，但原文既未说明其不面向玩家体验，也未描述任何循环关系，故按『不确定时判为未通过』处理。」

→ **我加的两条规则互相冲突**：例外条款用**许可性**措辞（"**可**判为不适用"），判定纪律用**强制性**措辞（"不确定时判为未通过"）。冲突时，后者胜出。
→ **教训：许可性措辞在 LLM 判定任务里几乎等于没有；规则之间必须显式声明优先级。**

**4. 唯一一条漏判，恰好是全项目最有说服力的一条**
`v1b` 与 `v2` **都放行了 R21**（人工判 `core_loop` 缺失）。`v2` 给的理由是：

> 原文：『当玩家在 1.5 秒内依次释放 A 技能（突进）和 B 技能（斩击）时，B 技能按钮周围出现一圈高亮呼吸效果，提示该次释放会触发连招加成（伤害 +20%）』；判定：写明了玩…

它**把"动作 + 反馈"当成了"核心循环"**，忽略了规则要求的第三个要素（与既有玩法循环的关系）。而人工标注抓到了。
→ 这是「看起来合理、还引用了原文」的错误——**最危险的一类**，也是「为什么仍然需要人工评审」最直接的证据。

### 预测记录（两次都错，如实记录）

| 轮次 | 我的预测 | 结果 |
|---|---|---|
| 第一轮（20 条） | 预测 `v2` 最好 | ❌ 错。`v2` 比 `v1b` 低 5 个百分点 |
| 第二轮（30 条） | 预测"例外写进 rubric 后 `v2` 会改善或反超" | ❌ 又错。`v2` 仍低于 `v1b`，但查出了机制原因（规则内部冲突） |

**两次预测都错，但两次都查出了原因。** 这比"预测对了"更有价值：如果只报数字、不先立预测，就不会去追查 R04 的规则冲突，也发现不了「许可性措辞无效」这条——而它对写任何 GPT 判定类 prompt 都适用。

### 指标选择的说明

本数据集就绪率为 **30%（9/30）**，因此：

- **漏判率容易虚低**——"永远打回"同样能做到 0%；报告必须与懒惰基线**并列**呈现；
- **主指标应为误拦率**（分母 9，仍有统计局限，见下）；
- 评测脚本已内置两个懒惰基线，并对"输出不可解析"的版本自动标注「分项一致率不可解读」。

### 下一步（按优先级）

1. **修规则冲突**：把例外改成**强制性**措辞并显式声明优先级——"工程/工具类需求**直接视为通过**，该条**优先于**『不确定时判未通过』"。改完重跑 `v2`，与 `v1b` 对照。
2. **修 `dependencies` 的边界**：`v2` 判 R26 缺失、`v1b` 判通过——差别在于"已经给到我了 / 周五之前会交"算不算「确认性表述」。规则需要给正例。
3. **扩充就绪样本**：9 条仍偏少（错 1 条 = 11 个百分点）。

## 已知局限（如实记录）

1. **数据集是模拟的，而且需求文本全部由助手起草**（30 条）。作者的贡献是**判定方向与判定本身**，不是需求文本。这意味着文本可能**比真实需求更贴合规则结构**（起草时就知道有哪 8 项），也缺少真实需求的混乱度（错别字、口头语、跨文档引用、历史包袱）。→ **评测结果偏乐观**，不能等同于真实场景表现。
2. **人工标注不是独立标注**：R01–R20 中有 13 条由作者判定（其中 7 处经助手冲突提示后修订；另 7 条因原文信息过少，改由助手建议、作者确认）；R21–R30 为**作者盲判**（助手起草文本但不告知预设缺失项），判后经协商修订 7 处、1 处按宽口径裁定。因此本数据集属于「作者主导 + 助手参与」，主观性未被消除，**也没有第二人独立复核**（见 `reports/label-review-v1.md` 第八节与 `data/第二批样本与盲判记录.md`）。这恰好是真实评审的缩影：两位评审人对同一条需求也可能不一致。
3. **部分判定项在文本层面天然难以判定**：例如「依赖方已确认」的真实状态不在需求文本里，模型只能看到"写了/没写"，看不到"是否真的确认过"。这是本方法的**能力上限**，不是调 prompt 能解决的。
4. **`one_liner`（一句话说得清）区分度偏低**：30 条中被判定缺失仅 **3 次（10%）**，而最高的 `risk_and_cut` 为 **16/30（53%）**。该项的一致率容易虚高，解读评测结果时必须单独说明或剔除。
5. mock 模式的输出由关键词启发式生成，**与模型能力无关，任何情况下都不得作为效果证据**。
6. **规则本身对"工程向需求"适配不良**：`core_loop`（核心循环）对内部工具/管线类需求无意义（例如 R04）。该缺陷已于 v0.3 修复——例外条款写进了 `rubric.py`。**但实测发现模型仍会推翻它**：例外用的是**许可性**措辞（"可判为不适用"），与"不确定时判未通过"的**强制性**纪律冲突时，后者胜出。详见「结果」第 3 条。
7. **"就绪"样本仅 3 条**（**已于 2026-10-05 修复**：数据集扩充至 30 条，就绪样本 9 条）。原问题：误拦率的分母只有 3，且全部版本差异都产生在这 3 条上，结论置信度极低。
8. **评测存在不对等约定**（**已修复**：该例外条款已写入 `rubric.py`，`v2` 的 prompt 会内嵌它，`v1b` 仍不知道——这本身成为一个可对照的变量）。
9. **工具健壮性的已知边界，其中一处是 prompt 设计引入的问题**
   `v2` 的 prompt 要求「`reason` 必须引用需求原文片段」，这**提高了输出 JSON 的破损概率**——模型引用原文时会写出未转义的 ASCII 引号，使整个响应不再是合法 JSON。
   已采取三层应对：① **括号配平扫描 + 尾随逗号修复**（实测可救回 6/7 类坏 JSON）；② 解析失败时**追加纠错提示重试**；③ **单条失败不再中断整轮**，按「未通过」记录并在报告中自动标注「不反映模型能力」。
   **仍未解决**：字符串内未转义的引号属于 JSON 文法歧义，无法自动修复，只能依赖重试。这是「要求模型引用原文」与「要求严格 JSON」之间的真实张力——**格式约束越强，越要和内容要求权衡**。

## 与《游戏项目研发流程规范》的关系

本工具的评分规则**完全来自**配套仓库 `game-pm-playbook` 中的 `03-检查清单/DoR-需求就绪定义.md`。

这个顺序很重要：**先有规范，再谈自动化**。反过来的话，工具会变成一个没有标准的玩具——你不知道它判得对不对，也无法解释它为什么打回一条需求。

反过来也成立：**工具会反哺规范**。本次评测暴露了 DoR 三处措辞的歧义（详见「结果」与 `game-pm-playbook` 的 v0.3 修订记录），说明规范可以被检验、也应该被迭代。
